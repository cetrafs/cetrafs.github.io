faq:
  - question: "Is cetrafs an alternative to VMFS?"
    answer: "Yes. It uses the same model: several hypervisors mount one shared LUN, each runs its own VMs, the disk images live directly on the volume, and nodes coordinate through the storage with SCSI COMPARE AND WRITE (VMware calls it ATS). cetrafs runs on a standard Linux kernel, and its on-disk format is open. See [cetrafs vs VMFS](/docs/concepts/vs-vmfs/)."
  - question: "How is it different from GFS2 or OCFS2?"
    answer: "GFS2 and OCFS2 are general-purpose POSIX cluster filesystems, coordinated by a distributed lock manager over the network. cetrafs is built only for VM images, which usually have a single writer, so it can lock whole files and coordinate through the LUN alone. If many hosts must write the same files at once, use GFS2 or OCFS2. See [cetrafs vs GFS2](/docs/concepts/vs-gfs2/)."
  - question: "Do I need a DLM, corosync or pacemaker?"
    answer: "Not for the filesystem. cetrafs has no lock manager and no network protocol in the data path. A multi-node production cluster still needs a cluster manager that can **fence** (power off) a hung host, such as Proxmox HA, because cetrafs can fence itself but not other hosts. See [Fencing and split-brain](/docs/concepts/fencing/)."
  - question: "What storage does it need?"
    answer: "Any block device works for a single node. For a cluster, every node needs the same iSCSI or Fibre Channel LUN, and the LUN must support SCSI COMPARE AND WRITE (opcode `0x89`). Multipath devices are supported. See [Check a LUN for atomic CAW](/docs/how-tos/check-caw/)."
  - question: "Can I use it without COMPARE AND WRITE?"
    answer: "Yes, but only one host can mount the volume at a time. While it is mounted, a mount on any other host fails with `EBUSY`. Loop devices, local disks and NVMe devices fall into this category."
  - question: "Does it work with NVMe or NVMe over Fabrics?"
    answer: "It depends on the protocol the host uses, not on the drives. **NVMe drives exported over SCSI are supported.** An array that presents its NVMe drives as iSCSI or Fibre Channel LUNs gives the host an ordinary SCSI device, and if the array supports COMPARE AND WRITE, several nodes can mount it. **NVMe over Fabrics, such as NVMe over FC, is a different protocol and is not supported yet.** The host sees a native NVMe device (`/dev/nvme...`), as with a local NVMe drive, and cetrafs has no atomic compare-and-write for NVMe, so such a device works on a single node only. The code already has the hooks for an NVMe compare-and-write, but the developers have no NVMe over FC hardware to test it on, and it won't be supported until they can reach some. To see which kind of device cetrafs finds, [check the LUN for atomic CAW](/docs/how-tos/check-caw/)."
  - question: "Does it work with Proxmox VE?"
    answer: "Yes. The [storage plugin](/docs/how-tos/proxmox-plugin/) adds a `cetrafs` storage type: Proxmox mounts the volume on every node with the `nofilelock` option, which live migration on Proxmox needs, and uses it as shared storage. An optional package adds it to the web UI. Both cetrafs and the plugin are published as Debian packages: see [Install on Proxmox VE](/docs/how-tos/install-proxmox/). You can also mount the volume yourself and add it as shared directory storage, as in [Build a Proxmox VE shared datastore](/docs/tutorials/proxmox-datastore/), and see [Shared storage for Proxmox VE without Ceph](/docs/concepts/proxmox-shared-storage/) for how it compares to the other options."
  - question: "Which VM disk formats can I use?"
    answer: "Any image file: raw, qcow2 or vmdk. Raw is recommended: qcow2 scatters its allocations and fragments badly. Use `cache=none` and `aio=threads`. See [Configure VM disks for cetrafs](/docs/how-tos/configure-vm-disks/)."
  - question: "Does cetrafs support thin provisioning?"
    answer: "Yes, at both levels. On the volume, a raw image only uses the blocks actually written, and `SEEK_HOLE`/`SEEK_DATA` and `FIEMAP` let `cp --sparse=auto`, `tar -S` and `qemu-img convert` keep holes. Hole punching and `ZERO_RANGE` are supported, so a guest's TRIM, through qemu `discard=on`, shrinks its image. On a thin LUN, cetrafs gives freed space back to the array with UNMAP: automatically when a Block Group empties, with `fstrim`, or as space is freed with `-o discard`. See [Return free space to a thin LUN](/docs/how-tos/reclaim-thin-space/)."
  - question: "Can two hosts write the same file at the same time?"
    answer: "Not by default. A file opened for writing is locked to one node, and other nodes get `Text file busy`. With the `nofilelock` mount option, which live migration on Proxmox VE needs, cetrafs no longer prevents it. Then only Proxmox's cluster layer keeps writers apart, because Proxmox turns qemu's own image locking off. See [why `nofilelock` exists](/docs/how-tos/live-migration/#why-proxmox-needs-it-image-locking-is-turned-off)."
  - question: "What happens when a node crashes?"
    answer: "The surviving nodes need no intervention. Once the dead node's heartbeat has been silent for the stale window (120 s by default), a survivor replays its journal and then takes over its regions and locks. An HA agent that has powered the host off can declare it dead at once instead. If the node was only hung, it stops writing on its own before its peers take over, and stays stopped until it is remounted. No `fsck` is needed afterwards. See [Recover from a node failure](/docs/how-tos/recover-node-failure/)."
  - question: "How many nodes and how large a file can it handle?"
    answer: "Up to 64 nodes per volume, and files up to 1 EiB with up to about 65 million extents each. A directory holds up to about 3.9 million entries. A volume lives on one block device and can be grown while mounted. See [Limits and unsupported operations](/docs/reference/limits/)."
  - question: "How is cetrafs tested?"
    answer: "With more than 900 regression suites, most of them proven to fail without the fix they guard, a content oracle that checks every block it wrote, randomized model checkers, a crash rig, image fuzzers, a KASAN build, and a two-node suite on real SAN storage. A full run of the main gate takes about 8 hours on one machine. See [How cetrafs is tested](/docs/concepts/testing/)."
  - question: "Which kernels are supported?"
    answer: "Linux `7.0.14`, `7.1.8+deb13` (Debian), `7.2.11` and `7.3.4` (Debian), and Proxmox VE `7.0.14-*-pve` and `7.3.6-1-pve`, on amd64 and arm64. DKMS builds the module for kernels 7.0 to 7.3. See [Project status](/docs/intro/status/)."
  - question: "Is it ready for production?"
    answer: "Yes, for its target workload: VM disk images on a shared LUN with COMPARE AND WRITE. Every change passes more than 900 regression suites and about 6,600 assertions, two-node scenarios on real Fibre Channel and iSCSI storage, crash replay and fuzzing, and the list of known open defects is empty. Validate your own storage path before the first deployment, and keep backups, as with any storage. See [How cetrafs is tested](/docs/concepts/testing/) and [Validate a storage stack before deployment](/docs/how-tos/validate-storage-stack/)."
  - question: "Can I upgrade without reformatting?"
    answer: "Between releases with the same on-disk format version, yes, one node at a time. Across a format change, no: you move the data off, reformat and restore. The move from 0.9.x to 0.10 is such a change. See [Upgrade to a new format version](/docs/how-tos/upgrade-reformat/)."
